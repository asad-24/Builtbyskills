# Profile self-update security verification

Run `profile_self_updates.sql` against a **disposable Supabase database**, as
`postgres`, after applying all repository migrations in timestamp order. Do not
run seeds. The script creates its own Auth/profile fixtures and rolls back every
fixture and temporary grant. It stops on unexpected errors; closing a failed psql
session also rolls back its transaction. Fixed fixture IDs intentionally fail on
collision instead of altering existing records.

For a local Supabase database with the standard local connection settings:

```powershell
psql -X -h 127.0.0.1 -p 54322 -U postgres -d postgres -W -v ON_ERROR_STOP=1 -f supabase/migrations/202609140001_secure_profile_self_updates.sql
psql -X -h 127.0.0.1 -p 54322 -U postgres -d postgres -W -v ON_ERROR_STOP=1 -f supabase/tests/profile_self_updates.sql
```

The first command applies only this new migration; omit it if your migration
runner already applied it. Earlier migrations must already be installed. Enter
the local database password at the prompt. Never point these commands at a
production database. No local database tooling/configuration is supplied here.

The executable SQL switches the actual database role to `authenticated` and sets
Supabase JWT claims. It proves (with broad UPDATE grants deliberately present):

- A student cannot change role, status, Auth linkage (including null), profile ID,
  email, or creation time: each statement must raise SQLSTATE `42501`.
- Updating another user's personal information affects zero rows under RLS.
- Name, phone, WhatsApp, and avatar edits succeed; unchanged protected values are
  accepted and `updated_at` is still generated by the existing timestamp trigger.
- An active super admin can change another profile's role/status.
- A suspended instructor cannot reactivate/promote themselves.
- `service_role` can insert, upsert role/status by email, and link Auth identities,
  even with a non-admin JWT subject. Final assertions verify persisted values.

Expect PASS notices, a ROLLBACK, and the final success message. These are real SQL
authorization scenarios, not mocked Vitest tests. They have not been executed
unless the implementation report explicitly records a database run.

## Boundary and preserved behavior

The new SECURITY INVOKER trigger compares OLD/NEW values using IS DISTINCT FROM.
Existing RLS continues to decide row access. Actual `service_role`, `postgres`,
and `supabase_admin` callers, plus authenticated active super admins checked by
the existing database helper, may manage protected fields. User metadata is not
trusted. Do not convert the trigger function to SECURITY DEFINER.

Email is protected because provisioning uses it as an identity/conflict key;
changing profile email alone does not update Supabase Auth email. Profile ID and
creation time are also not personal-edit fields. The current profile/security
page is read-only, but ordinary personal fields remain editable through the
existing RLS self-update path. The existing timestamp trigger overrides supplied
`updated_at`, so it remains database-controlled.

This migration does not repair previously modified profiles. Review existing
role/status/Auth/email mappings against trusted records before relying on them:
an already active super-admin profile remains authorized. Apply through the
normal migration process; adding a migration file alone does not secure a
deployed database. Any privileged SECURITY DEFINER functions or extra policies
added outside this repository require separate review.
